# Cocos Creator 编辑器操作规程(Editor Operation Protocol)

> 本文是 Agent 操作 Cocos Creator 编辑器的硬性规程,源自 2026-09-04 的双实例事故复盘。
> 对任何 GUI 应用(Unity、Blender、PS)同样适用,换名字即可复用。

## 事故档案(为什么有这份规程)

时间线:

1. 用户说"装完了"(只说了安装位置,未说编辑器是否已打开);
2. Agent 未查进程,直接命令行启动编辑器 → 与用户已打开的实例撞车:双实例抢 7420 端口与日志文件锁;
3. 启动日志里的冲突信号(`EPERM: project.log 被锁`、`GPU cache 拒绝访问`)被标注为"非致命"放过;
4. 编辑器卡死后,用户要求重试;Agent `taskkill /IM` 全杀——**把用户的实例一并杀掉**;
5. Agent 再次命令行启动新实例;随后又与用户重新打开的实例形成第二个双实例;
6. 清理时 Agent 按启动时间戳猜测实例归属,**猜反方向,第二次杀掉用户的实例**。

根因:启动前无进程识别;冲突信号被忽略;全杀不分归属;归属靠猜不确认。

## 规程

### R1 所有权:编辑器的启动权归用户

- Agent 默认**永不主动启动** GUI 应用;操作对象永远是"用户已打开的实例"。
- 仅当用户明确说"你来启动"时,Agent 才可启动,且启动前必须完成 R2。
- 例外:无 GUI 的进程(构建脚本、CLI 工具)不受此限。

### R2 启动前三查(Agent 获得启动授权时也必须执行)

1. `tasklist` 查目标应用进程是否已存在;
2. 存在则识别实例:窗口标题、启动时间、命令行参数(`wmic process get commandline`),向用户报告现状;
3. 有现存实例 → 在其上操作;确需新实例 → 向用户说明理由并确认。

### R3 冲突信号即停

以下信号 = 强烈暗示"已有实例在跑",遇到任何一个:停止当前动作,核实实例状态,向用户报告:

- 日志/配置文件 `EPERM` 被锁;
- 缓存创建失败、单实例锁转发;
- `EADDRINUSE` 端口占用(另一实例加载了同一扩展/服务);
- 应用窗口标题出现异常前缀(如 `Untitled`)或进程数异常增长。

**禁止**把它们标注为"非致命警告"后继续执行。

### R4 清理必确认归属

- Agent 启动的任何进程,启动时**当场记录 PID**到工作日志,清理时凭 PID 精确击杀(`/PID`,不是 `/IM`);
- 杀进程前回答"这个实例是谁开的":不确定 = 问用户,不猜时间戳;
- `taskkill /IM` 全杀只允许在用户明确说"全部关掉"时使用。

### R5 恢复交还启动权

事故后 Agent 只负责清理到干净状态(无残留实例、无端口占用、无文件锁),然后**把启动权交还用户**:"请你重新打开"。Agent 不替用户重建现场,除非被要求。

## GUI 操作附则(Windows)

- 原始坐标点击要求目标窗口处于前台;点击前先激活窗口(`activate`),每次点击前窗口身份必须重新验证;
- Cocos Creator(Electron)默认不暴露无障碍树(`get_app_state` 只有空元素)——对它的全部 GUI 操作走"截图 + 坐标"路线,这正印证了本项目感知层存在的意义;
- Agent 与用户共用一台机器时,抢焦点操作(激活+点击)应集中批量执行,并提前告知用户"接下来十几秒屏幕焦点会被抢占"。
