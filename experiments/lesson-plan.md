# 对照实验教案:感知注入对 GUI Agent 操作 Cocos Creator 的影响

## 实验目的

用同一组任务、同一台机器、同一个 GUI Agent,对比三种自动化层级的成功率和成本,验证核心论点:

> **Agent 的注意力是稀缺资源;结构化感知把注意力从"找"解放到"做"。**
> 视觉模型能力不足造成的定位/验证失败,可以被真值感知层(而非更强的视觉模型)直接修复。

## 变量定义

| 组别 | 操作方式 | 感知方式 | 需要准备 |
|---|---|---|---|
| A 纯 GUI | 截图 + 坐标点击 + 拖拽 | 仅视觉模型 | computer-use 环境(ZCode / UI-TARS Desktop / Claude Computer Use) |
| B GUI + 感知 | 同 A | A + cocos-sense(操作后必调 `selected_nodes` / `scene_tree` 回读) | A + 本扩展 |
| C 文件直写 | 直接生成/修改 `.scene` `.prefab` `.ts` | asset-db 自动刷新 + 构建验证 | 任意编程 Agent |

B 组操作规程(关键):**每次 GUI 操作后必须回读**——点选后查 `selected_nodes` 比对 UUID;结构调整后查 `scene_tree` 比对节点存在性与坐标;失败则基于真值重试,禁止凭截图"感觉对了"。

## 任务集(由易到难)

| 编号 | 任务 | 考察点 |
|---|---|---|
| T1 | 创建空节点,命名 `Player`,挂 `cc.Sprite`,指定一张项目内图片 | 面板导航、属性填写、资源选择 |
| T2 | 把某个 prefab 从资源管理器拖入场景视图,放到画布中心附近 | **拖拽 + canvas 视觉定位**(预期 A 组主要翻车点) |
| T3 | 搭一个关卡:地面 + 3 个平台 + 1 个敌人节点,层级正确命名 | 多步操作、长时程一致性、回读纠偏 |
| T4 | 批量生成 5 个关卡(节点结构相同、参数不同) | 规模化:预期 C 组碾压性优势 |

## 指标

- **任务完成率**(0/0.5/1:失败 / 完成但有偏差 / 完全正确)
- **GUI 步骤数**(点击+拖拽+按键次数)
- **VLM 推理次数**(A/B 组,即截图决策轮数)
- **总 token 消耗**(B 组含感知回读的 token——记录,用于回答"感知的 token 成本是否值回票价")
- **墙钟时间**
- **纠偏次数**(B 组:回读发现错误并修正的次数;A 组此指标无法观测,记 N/A——这本身就是论点的一部分)

## 预期结果(实验前登记,防事后归因)

- A 组:T1 勉强可成;T2 拖拽大概率失败或位置偏差大;T3 中途偏离率高;T4 基本不可行。
- B 组:T2 的成功率提升最大(拖拽目标坐标由真值给出);T3 靠回读纠偏收敛;token 比A 高(多出回读),但总成本低于 A(重试轮数骤减)。
- C 组:T1–T3 快而稳,T4 出现数量级优势;但"跑起来看效果"仍需回到 GUI——引出分层结论。

## 记录表模板

每任务每组一行:

```
任务 | 组别 | 完成(0/0.5/1) | GUI步数 | VLM轮数 | token | 耗时 | 纠偏次数 | 翻车现场描述(截图/日志)
```

## 教学讨论题

1. B 组比 A 组多花的 token(感知回读),买到了什么?用纠偏次数和完成率算这笔账。
2. T2 里 Agent 的坐标从哪来?A 组(视觉估算)和 B 组(世界坐标真值)的误差差几个数量级?
3. C 组赢了 T4,为什么"跑起来看效果"还是要回到 GUI?——引出分层架构:文件直写(结构)> 感知+GUI(验收)> 纯 GUI(长尾)。
4. 如果视觉模型明年强 10 倍,B 组还有价值吗?(引导出:真值的边际价值在"验证"而非"定位",验证需求的下降速度远慢于定位。)
