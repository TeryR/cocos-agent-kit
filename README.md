# cocos-sense — Cocos 专用 Agent 的感知器官

> **最终形态**:一个 Cocos 专用 Agent——tool calling 为主、GUI 兜底、文件直写管批量、感知贯穿全程。
> **本仓库现状**:那个 Agent 的第一个器官。0.1 阶段只做感知(结构化眼睛),0.2 长出操作工具(cocos-act),0.3 加 Agent 配置层。
>
> 感知是器官,操作是目的。单独先做感知,是因为:生态里唯独它真缺;所有操作通道都靠它验证;没有它连操作工具都无法调试。

## 定位:生产优先,实验是仪表不是目的

最终目标是**真实生产力**:Agent 能独立交付可运行、可发布的游戏内容。对照实验(T1-T4)不作为阶段性目标,而是生产过程中的**诊断工具**——垂直闭环中哪个环节失败,用对照组实验定位是感知、操作还是模型的问题。

生产化的四个硬指标(gate):

| Gate | 指标 | 目标 |
|---|---|---|
| 交付 | PRD 级描述 → 可运行游戏的成功率 | 常见品类 >80% |
| 自修复 | 编译/运行报错后无人工介入恢复率 | >90%(直接压在感知层上) |
| 效率 | vs 熟练人工 | 原型 5-10x,批量内容 50x+ |
| 成本 | 单关卡/角色产出成本 | < 人工 1/10 |

**首要生产场景**:中国小游戏(数据驱动品类)的内容产能——关卡批量生产、玩法原型快速迭代。这是真实产能痛点,也是 Cocos 引擎的主场。

**相对现有 AI 工具的本质差异**:Cursor/Copilot 的闭环止步于代码;本架构的闭环延伸到编辑器状态与运行时表现——AI 写完代码自己跑、自己看到角色没动、自己查到组件没挂、自己修。游戏的正确性不在代码里,在跑起来的表现里,这个闭环目前没有工具做到。

## 最终形态:Cocos 专用 Agent 的总架构

"专用"的是器官和知识,不是大脑——用现成 Agent runtime(ZCode / Claude Code)作编排层,不自己写 agent loop:

```
                ┌──────────────────────────────────┐
                │      Cocos 专用 Agent(编排层)       │
                │   领域提示 + 工作流技能 + 验证清单     │
                └───┬──────────┬──────────┬────────┘
        tool calling│          │          │ computer-use
        (主通道)     │          │          │ (兜底+验收)
   ┌────────────────▼───┐ ┌────▼────────┐ ┌───▼──────────────┐
   │ cocos 扩展(MCP)      │ │ GUI 通道     │ │ 文件直写           │
   │ ├ 感知工具(cocos-sense)│ │ 鼠标键盘/截图 │ │ .scene/.prefab/.ts│
   │ └ 操作工具(cocos-act) │ └─────────────┘ │ (批量生成关卡)      │
   │   返回值=操作后状态回读  │                 └──────────────────┘
   └─────────┬──────────┘
             ▼
      Cocos Creator 编辑器
```

**为什么 tool calling 是主通道,而不是我们最初设想的"GUI 操作为主"?** "GUI 为主"是对现状的诊断:现有操作型 MCP 效果差,Agent 不得不靠鼠标键盘。但根因(盲操作、工具爆炸、粒度错配)都是可修的工程问题:盲操作的修法是**每个操作工具的返回值自带操作后状态回读**(act-then-verify 内建于工具,现有 MCP 全都没做);工具爆炸的修法是意图级工具(≤15 个)。修完之后,tool calling 对确定性操作全面优于 GUI,GUI 退到真正不可替代的位置——无 API 的长尾操作 + 人的验收环节(预览、试玩)。

## 为什么是"感知"而不是"操作"(0.1 阶段定位)

1. **视觉模型对场景视图是盲的。** Cocos Creator 的场景视图是 WebGL canvas,截图里只有像素,VLM 说不出"Player 节点在坐标 (712, 384)"。感知层把这组真值直接给它。
2. **操作型 MCP 有两个顽疾:工具爆炸 + 盲操作。** 几百个 API 级工具让模型选择准确率下降;API 返回 success 不等于编辑器状态正确,错误层层累积。感知层反其道而行:工具极少(全只读),价值在于让 GUI 每一步操作后都能**回读验证**。
3. **GUI 擅长交互反馈,结构化擅长精确语义。** 两者拼起来才是完整的"像人一样操作":人也是看着屏幕(视觉)+ 感知界面状态(结构化直觉)来操作的。

## 架构

```
┌────────────────────────────────────────────────┐
│           外部 GUI Agent(Claude / ZCode / UI-TARS)│
│      看:截图 + 视觉模型        动:鼠标键盘        │
└─────────┬─────────────────────────┬────────────┘
          │ POST /mcp(JSON-RPC)     │ 点击 / 拖拽 / 输入
          ▼                         ▼
┌─────────────────────┐   ┌────────────────────────────┐
│  cocos-sense 扩展    │   │   Cocos Creator 编辑器       │
│  (只读 MCP server)   │   │   场景视图 / 层级面板 / 检查器  │
│  127.0.0.1:7420/mcp │   │   (Agent 的 GUI 操作对象)     │
└─────────┬───────────┘   └────────────────────────────┘
          │ Editor.Message / execute-scene-script
          ▼
┌─────────────────────┐
│   场景进程(cc 引擎)   │
│  真值:树/坐标/组件    │
└─────────────────────┘
```

MCP server 直接内嵌在编辑器扩展里,零 npm 依赖,拷贝即用,不需要独立进程。

## 当前感知接口(0.1)

| 工具 | 作用 | 状态 |
|---|---|---|
| `scene_tree` | 意图级场景树:名称、UUID、世界坐标、激活状态、组件类名 | ✅ 待真机校准 |
| `node_detail` | 单节点详情(父节点、缩放、子节点列表) | ✅ 待真机校准 |
| `selected_nodes` | 当前选中节点回读——**GUI 点击/拖拽后的验证锚点** | ⚠️ API 待校准 |
| `asset_index` | 资产索引(名称、类型、URL) | ✅ 待真机校准 |

"待真机校准"的含义见 `docs/design.md` 的校准清单:代码里的 API 调用基于公开文档与惯用签名,首次在真实 Cocos Creator 3.8.x 里加载后需逐项核对,字段映射已在代码中做防御性处理。

## 快速开始(5 分钟,从 fork 到可用)

### 前置条件

- Cocos Creator **3.8.x**(3.8.6+ 实测过,3.7 未验证)
- 任意支持 MCP(Streamable HTTP)的 Agent 客户端:Claude Code / Cursor / Cline / ZCode 等
- 一个你自己的 Cocos 游戏项目

### 第 1 步:安装扩展

把本仓库的 `extension/` 文件夹整体拷贝到你项目的 `extensions/cocos-sense/`(没有 `extensions` 目录就新建):

```
你的项目/
└── extensions/
    └── cocos-sense/        ← extension/ 的内容
        ├── package.json
        ├── main.js
        └── ...
```

### 第 2 步:启用

打开/刷新项目——项目内扩展**默认自动启用**。若没启用,扩展管理器 → 扩展 → cocos-sense → 开关打开。

### 第 3 步:验证服务

```bash
curl http://127.0.0.1:7420/health
# {"ok":true,"server":{"name":"cocos-sense","version":"0.2.0"}}
```

### 第 4 步:接入你的 Agent

**Claude Code:**
```bash
claude mcp add --transport http cocos-sense http://127.0.0.1:7420/mcp
```

**Cursor / Cline 等**(mcp.json):
```json
{
  "mcpServers": {
    "cocos-sense": { "url": "http://127.0.0.1:7420/mcp" }
  }
}
```

### 第 5 步:冒烟测试

对你的 Agent 说:**"列出当前 Cocos 场景的节点树"**。它调用 `scene_tree` 并返回真实场景数据(节点名/UUID/世界坐标/组件)= 全链路打通。

### 第 6 步(推荐):安装 Skill,让 Agent 会"正确地"用这些工具

工具只是能力,`skills/cocos-sense/SKILL.md` 是使用这些能力的作业指导书:感知→操作→验证→保存的工作流、坐标系与设计分辨率知识、act-then-verify 铁律、资源显示异常的诊断指引。

- **Claude Code**:拷贝到 `~/.claude/skills/cocos-sense/SKILL.md`(全局)或项目 `.claude/skills/cocos-sense/SKILL.md`(项目级);
- **ZCode / 其他支持 Agent Skills 规范的客户端**:同理放入其 skills 目录;
- 不装也能用(工具是标准的),但装上后 Agent 少走弯路:先感知后动手、检查回读、保存习惯、坐标换算——这些纪律都写在里面。

### 排查表

| 症状 | 原因与解法 |
|---|---|
| `/health` 不通 | 扩展未启用 → 扩展管理器检查;或开了多个编辑器实例抢 7420 → **关掉多余的编辑器**(单端口单实例) |
| 编辑器控制台报 `EADDRINUSE` | 同上,另一个实例占了端口 |
| 场景树返回 error: no active scene | 编辑器里还没打开任何场景 → 双击一个 .scene |
| 工具调用报 spread / undefined 错误 | 你拿到的是旧版扩展,拉最新仓库并重新加载 |

### ⚠️ 安全须知

- `act_` 系列工具会**真实修改你的场景**并可通过 `save_scene` 落盘——操作前请确保项目在 git 干净状态,或已手动保存备份;
- 感知工具全部只读,无风险;
- 服务只监听 `127.0.0.1`,不对外网暴露。

## 路线图

- **0.1** 感知模块:场景树 / 节点详情 / 选中回读 / 资产索引(本版,骨架就位待真机校准)
- **0.2** 操作模块 cocos-act:意图级 ≤15 个工具(创建/删除节点、挂组件、设属性、存 prefab、刷新资源库、执行菜单命令…),**每个返回值带操作后状态回读**——act-then-verify 内建于工具,这是相对现有所有 MCP 的本质改进
- **0.3** Agent 配置层:领域知识配置(坐标系统、.scene 格式要点、组件体系、常见坑)+ 工作流技能(make_character / make_level 的确定性步骤)
- **0.4** 控制台错误流、场景视图屏幕坐标投影(canvas 真值)、Set-of-Mark
- **0.5** 三组对照实验完整跑通,产出实验报告:感知注入对 GUI Agent 成功率的影响 + tool calling/GUI/文件直写三层各自的适用边界

## 与生态内已有方案的关系

- **daxianlee/cocos-mcp-server(开源版/Pro 版)**:操作型,工具面大;Pro 版的意图级压缩是付费点。cocos-sense 与其正交:一个管"做",一个管"看"。
- **Game Agent(商城插件)**:编辑器内嵌智能体,语义层感知做得好,但像素层靠 VLM 硬看(作者原话:"视觉能力差的效果就不好"),且外部 AI 接不上。
- **官方 PinK**:AI 原生新编辑器,服务新项目;cocos-sense 服务**存量 Creator 项目 + 任意外部 Agent** 的组合,这是两条路都覆盖不到的位置。
